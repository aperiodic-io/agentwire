A compression codec for LLM logs and traces

Keep every prompt, at a hundredth of the bytes.

Every LLM call is logged with its whole prompt, and every prompt is the previous prompt plus one turn. Deltapack stores each record as a delta against the earlier record it shares the most with: about 100× smaller, byte-exact, and any record reads back on its own.

    Why

    Most of your log is copies of what it already holds

    A 200-step agent run writes its system prompt and tool schemas into your log 200 times, its first tool result 199 times. At a hundredth of the bytes you can keep every request in full, without sampling or truncating, and still pull any one out in milliseconds.

    Replay a failure

    deltapack log get writes a recorded request byte for byte, as the provider received it: post it again, or step through what the agent saw.

    Find a trace

    log show --trace <id> writes each of its spans as a line of JSON, prompt and attributes decoded from OTLP.

    Build an eval set

    log show --since 7d into jq, DuckDB or pandas: every prompt in full, not sampled or truncated.

    Answer an auditor

    Keep every request as long as you must with --keep-days, or hand each closed file to your archive with --on-rotate.

    Keep your backend

    --forward stores each batch, then passes it on to Langfuse, Phoenix, Honeycomb or any OTLP endpoint. It can sample; you still hold every span.

    Know what it saves

    deltapack log stats gives the ratio on your own traffic, file by file.

    Quick start

    Point your OpenTelemetry exporter at it

    Your agent, framework or gateway most likely exports OpenTelemetry already. Run a collector, set one variable, and every span and log record is stored on your disk. Nothing sits in the path of your model calls.

    Install
    cargo install deltapack --features proxy
# or: pip install deltapack-cli · brew install deltapack · ghcr.io/aperiodic-io/deltapack
    Run the collector
    deltapack collect --record-dir ~/deltapack   # OTLP/HTTP on :4318, OTLP/gRPC on :4317
    Point the exporter at it
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    Read it back
    deltapack log stats ~/deltapack/*.dpk   # records, their bytes, bytes on disk, ratio
deltapack log show  ~/deltapack/*.dpk   # one JSON line per span or log record

    Takes OTLP traces, logs and metrics, as protobuf or JSON, compressed or not. Most exporters leave prompts out until asked: the integrations guide has the flag for each tool. Also a recording proxy, a gateway log sink, a CLI for files you already have, and a library for Rust and Python.

    Why a block compressor loses

    It only sees one block. With 16 agents running, the previous copy of a prompt usually sits in another block, and a late prompt is larger than a block anyway. Deltapack looks for the previous copy by record, whatever its size.

    How it works

    A record costs about its new bytes

    Each record is a delta against one of the last records: it copies the unchanged start and end of that record and carries the edited middle as one Zstandard frame, which may reference the old middle, so content that moved is still found.

    What your log holds

    systemtoolsturn 1
    systemtoolsturn 1turn 2
    systemtoolsturn 1turn 2turn 3

    What deltapack stores

    systemtoolsturn 1
    +turn 2
    +turn 3

    Lossless

    Every record carries the SHA-256 of its body and is checked when read. A file that does not rebuild what it names is an error, never wrong bytes.

    Any record on its own

    In 64 ms on the benchmark, without unpacking the file. The chain of deltas behind a record is bounded.

    Crash-safe

    A crash loses at most the record being written. A file that ends mid-record still holds every record before it.

    Never in the way

    A failed write is counted in a metric and the request goes on. Recording never takes your traffic down.

    No credentials stored

    Headers are never stored. --key-file seals every body with a key you hold; --key-dir gives each tenant its own.

    A small, public format

    A file of Zstandard frames, each behind a few varints, specified in SPEC.md. Tested with property tests, Kani proofs, fuzzing and mutation testing.

    DPD1 · on the wire

    The same delta shrinks the request

    An agent that uploads its whole conversation on every call can send each request as a delta against the last one; the server rebuilds the exact body before the provider sees it. A 6 MiB request that adds one turn crosses the network as 141 bytes.

    What it is not

    Keep your backend for search; keep deltapack for the bodies

    Not a query engine

    log show finds records by trace and time and writes JSON lines for other tools to query. Keep your tracing backend for search and dashboards.

    Not a general log compressor

    The gain comes from records that repeat earlier records, as LLM requests and spans do. On logs without that shape, expect what zstd gives.

    Not fast enough for everything

    One record per span writes at about 12 MB/s on one core, because each span is tried against several candidate bases.

    Not a redaction layer

    A record is the body as it was sent, which is what makes replay exact. Redact where the content is produced.
